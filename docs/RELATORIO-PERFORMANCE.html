Ótimo — base já eficiente, agora afinada

A auditoria confirmou que o projeto já era bem otimizado (RAF com gating, DPR limitado, fundo em cache, suspensão em segundo plano). Esta etapa adicionou ganhos seguros de composição na GPU e auto-simplificação por FPS para dispositivos fracos, sem qualquer mudança visual perceptível em aparelhos capazes.

📋 Resumo executivo

Diagnóstico honesto e o que mudou.

🔍 Diagnóstico

O loop de render já para quando ocioso (nada de RAF contínuo → economia de bateria), o DPR é limitado (≤1.75 em low-end, ≤2 Android), o fundo do tabuleiro é cacheado offscreen, o hover roda só no desktop com cache de célula, e há suspensão de áudio/timers em segundo plano. Arrays de partículas/floaters são limitados.

⚡ Ganhos adicionados

(1) Canvas opaco (alpha:false) → menos composição na GPU; (2) auto-simplificação por FPS: sob <45fps sustentado, desliga as sombras caras do canvas (drop-shadow dos 64 blocos + glow das partículas); (3) listeners de layout passivos.

🛡️ Preservação

Nenhuma regra, dificuldade, animação, UI, UX ou economia alterada. Em dispositivos capazes, _fxLow=false → todas as sombras/efeitos permanecem idênticos. Só degrada em aparelhos que não sustentam 60 FPS — exatamente o comportamento pedido.

✅ Verificação

87/87 testes (Vitest) verdes. Smoke no navegador: boot limpo, getContextAttributes().alpha === false, tabuleiro renderizado pixel-a-pixel equivalente (screenshots do mapa e do jogo).

🚀 Principais otimizações

Cada uma segura (sem mudança visual em aparelhos capazes).

Render Canvas opaco (alpha:false)

O contexto 2D passou a {alpha:false}. Como o fundo (_bgCache) cobre 100% do canvas a cada frame e o border-radius é aplicado via CSS, o canal alfa era desnecessário. Resultado: o compositor do WebView deixa de tratar o canvas como camada translúcida — menos trabalho de GPU e bateria, zero mudança visual.

Render Auto-simplify por FPS

Nova flag _fxLow lida 1×/frame de TBJuice.isLowPower() (monitor que ativa low-power após <45fps sustentado). Quando ativa, o drawBlock pula o shadowBlur/shadowOffsetY dos blocos e o drawParticles pula o glow — as duas operações de canvas mais caras (dezenas de sombras por frame). Recupera FPS em aparelhos fracos, mantendo a arte intacta nos demais.

Eventos Listeners passivos

resize, orientationchange e visualViewport.resize agora usam {passive:true} (não chamam preventDefault) — sinaliza ao navegador que não bloqueiam, melhorando a resposta durante rotação/reflow.

Confirmado OK Já eficiente

RAF com gating (para quando ocioso), DPR limitado, fundo em cache, hover só desktop + cache de célula/BFS, suspensão de áudio/timers em visibilitychange/pagehide, arrays limitados (splice), fontes assíncronas, mascote em SVG com loading="lazy".

Renderização · 92

RAF com gating, DPR limitado, fundo cacheado, canvas opaco e auto-simplify por FPS. Resta cachear os gradientes por bloco (alocação de 64/ frame) — deixado como pendência por risco visual.

DOM · 90

Sem manipulação em loop de frame; hover com cache de célula; HUD atualiza por jogada, não por frame. void offsetWidth é reflow intencional só ao mudar score.

CSS · 85

Modular e enxuto (47 KB). Usa backdrop-filter e animações de box-shadow (custosas) mantidas por serem parte do visual premium; candidatas a variantes leves em low-power.

JavaScript · 88

Módulos IIFE, funções puras testadas. O shell de gameplay ainda é grande (dívida arquitetural conhecida), mas os caminhos quentes são eficientes.

Memória · 90

Partículas/floaters/pops com splice; timers via AppTimers pausados em segundo plano; sem listeners órfãos (hover é único, não por evento).

Carregamento · 86

Scripts após o markup, fontes assíncronas, SVG lazy, SW precache. Pendente: concatenar/minificar CSS no build e minificar todos os JS.

Animações · 90

Canvas usa transform/alpha; CSS prioriza transform/opacity. Auto-simplify garante 60 FPS em aparelhos fracos.

Compatibilidade · 92

APIs com guards (try/catch, ?.), alpha:false e passivos são universais (Chrome/Edge/Safari iOS/Firefox). Web Audio/Haptics degradam com segurança.

🧭 Compatibilidade & segurança

🌐 Navegadores

  • {alpha:false} e {passive:true} — suporte universal
  • Web Audio / Vibrate / Haptics com fallback silencioso
  • visualViewport sob guard de existência
  • Sem APIs experimentais introduzidas nesta etapa

🔒 Segurança / robustez

  • Nenhuma nova entrada de dados externa
  • Caminhos de render dentro de try/catch existentes preservados
  • _fxLow é booleano interno, sem exposição/estado persistido
  • Sem alteração de save/economia/monetização
